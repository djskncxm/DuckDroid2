## 1. 结论

- `libmetasec_ml.so` 正常加载，`JNI_OnLoad` 的 `RegisterNatives` 绑定到
  `ms/bd/c/k3`；`Case::init` 的 7 个 selectors 全部通过，`god7`
  （模块 `+0x2e01c0`）返回 7 组头。
- 注入同一墙钟（`1792886400000` ms）时 **X-Khronos / X-Argus 与 DuckDroid
  参考 runner 逐字节一致**（`1792886400` / `gEbdag==`），与旧 README 的
  不变量一致；其余头含随机因子，不逐字节对拍。
- 严格 Java 世界只剩一条事件：`GetStaticMethodID(MS, "a", "()V")`。APK 里
  确实没有这个方法（`MS` 为空类，`MS0` 只有 `Bill/Louis/Zeoy/Francies`，
  `k3` 只有长签名 `a/c/b`），真机也会抛 `NoSuchMethodError` 后继续；
  gate 把它固定成“唯一允许的事件”。
- 新增 gate `07g_dy7_plugin`；全量 `ctest` 49/49，`build-werror` 通过，
  ASan-only 下 gate 通过（组合 ASan+UBSan 配置会停在 Unicorn 的
  softfloat `-fno-sanitize-recover` 上，属第三方，与本次代码无关）。

## 2. 项目结构

```text
code/user_code/dy7_case/
├── dy7_env.hpp/.cpp        # MS -> MS0 -> k3 层级、k3.a/c native、k3.b null 回调、Context
├── dy7_case.hpp/.cpp       # 7 个 selector 的初始化 + god7 调用
├── main.cpp                # 本地 runner（CLI + DY_* 兼容）
├── plugin.hpp/.cpp         # worker AppPlugin，app id dy7
├── dy7.properties          # Mi 8 / Android 12 (API 32) 画像
└── assets/libmetasec_ml.so # 4.3 MiB，从 APK lib/arm64-v8a 提取
```

接线沿用 jdgs/szstone：`main.cpp` 与 `plugin.cpp` 共享
`installEnvironment` → load libc → load 目标 → `Case::init`。对象图构建
（字符串、byte[]、Context、box 读取）放在 `dy7_env.cpp`，因为
`installJavaEnvironment` 只传函数指针；一个实例进程一次安装，与 worker 的
模型一致。

## 3. 平台包补了什么（`src/runtime/jni/envs/java_lang.cpp`）

| 面 | 原因 |
|---|---|
| `System.getProperty(Ljava/lang/String;)Ljava/lang/String;` | metasec 读 `os.arch`、`java.vm.*`；未知键返回 null。`ro.*` 不走这里（属性服务负责） |
| `java/lang/Thread` | `<init>()V`、`currentThread()`、`getName()`、`getStackTrace()`；宿主线程没有托管帧，故返回**空** `StackTraceElement[]` |
| `java/lang/Boolean` | `value:Z`、`<init>(Z)V`、`valueOf`、`booleanValue` |
| `java/lang/Long` | `value:J`、`<init>(J)V`、`valueOf`、`longValue` |
| `java/lang/Integer` | 原 `<init>` 之外补 `valueOf` / `intValue` |
| `envs::booleanValue` / `envs::longValue` | runner 从 native 返回的 box 对象里取值，和 `integerValue` 同层 |

项目包只保留 target 名字与设备值：`Context.getPackageName` 返回
`com.ss.android.ugc.aweme`，`getApplicationContext` 返回自身，`getFilesDir`
返回 null（与参考 runner 一致）。

## 4. runtime 补了什么

真实目标暴露了三处实现缺口，都是机制而不是目标特判：

1. **`futex` 的 bitset 变体**（`thread_handlers.cpp` / `thread_system.hpp` /
   `scheduler.cpp`）。libmetasec 的初始化线程用
   `FUTEX_WAIT_BITSET_PRIVATE`（`0x89`）等条件变量；M3 只实现
   `WAIT/WAKE`，未实现时返回 `-ENOSYS`，guest 原地重试。现在：
   `WAIT_BITSET` 的 timespec 按**绝对**时间解释（`FUTEX_CLOCK_REALTIME`
   用墙钟，否则单调钟），在 syscall 层换算成相对微秒再交给 scheduler；
   `WAKE_BITSET` 复用同一等待队列（每位都匹配）。timespec 的解析从
   scheduler 上移到 handler，因为时钟在 `SyscallContext` 里。
2. **`GetObjectRefType`**（JNI slot 232）。`RefTable::typeOf` 区分
   invalid/local/global，`JniState` 直接返回；metasec 用它决定要不要
   `NewGlobalRef`。
3. **主线程栈 4 MiB**（`RuntimeConfig::stack_size` 默认）。v5 签名会写到
   入口 SP 以下超过 64 KiB 的位置；旧 64 KiB 栈会触发
   `UC_ERR_WRITE_UNMAPPED`（`0x3ffffff0`，正是栈底再向下 16 字节），
   与 DuckDroid 参考引擎当年的修正一致。

另外把未实现 syscall 的日志补上了参数列表（`futex(0x..., 0x89, ...)`），
否则只能看到地址和 guest 栈，无法定位是哪个 op。

## 5. 验证

- `DY_WALL_TIME_MS=1792886400000`：
  - 本实现：`X-Argus: gEbdag==`，`X-Khronos: 1792886400`；
  - DuckDroid 参考 runner：相同。
- 固定 `--wall-time-ns`、`--monotonic-time-ns`、`--random-seed 7` 后，同一
  进程的两次实例 `X-Argus`/`X-Khronos` 相同。**整块头不承诺逐字节**：
  `X-Perseus` / `X-Gorgon` / `X-Ladon` 由 metasec 自己的 guest 线程并发取
  随机数，线程调度会让同一随机流的切分不同；跨进程两次实测相同是巧合，
  gate 只比较稳定头。
- gate `07g_dy7_plugin`：默认 instance-host 配置（含 5 s 单次调用超时）
  创建实例 → `make_app_plugin("dy7")` → init → `invoke(sign)`；断言
  `X-Khronos`、`X-Argus`、事件集合（只允许 `MS.a()V`），第二个实例比较
  稳定头。
- `--trace DIR`：`svc.log` + `insn/{code,bl,rw}.log` 正常产出；一次签名
  约 3.6 GB `code.log` + 3.9 GB `rw.log`，全模块 trace 需注意磁盘。
