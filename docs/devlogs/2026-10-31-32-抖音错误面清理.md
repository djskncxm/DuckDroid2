# 抖音签名错误面清理：nanosleep / ioctl / 信号

> 日期：2026-10-31
> 触发：单次 `duckemu_dy7_case` 签名在 stderr 留四条 WARN。
> 对照：`../DuckDroid/code/engine/os/os_state.cpp` 与 `vfs.cpp`。

## 1. 现象

注入墙钟后签名结果正确（`X-Argus: gEbdag==`、`X-Khronos: 1792886400`），
但一次调用固定产生四条 WARN（`DY_REPEAT=2` 也不会变多）：

```text
unsupported syscall tgkill(0x3e8, 0x4, 0x40)      # pid 1000, tid 4, SIGRTMAX
unsupported syscall nanosleep(0x..., 0x0)         # {tv_sec=0, tv_nsec=5000000}
jni missing-method class=.../MS name=a sig=()V    # APK 本身没有，已记录
unsupported syscall ioctl(0x3, 0x5401)            # fd 3, TCGETS
```

## 2. 定位

libmetasec 不经过 libc 的信号/睡眠封装，而是用自己的裸系统调用包装
（`0x29ec30`：`x8 = 立即数 - 233`）。三条调用都能落到具体代码：

| 调用 | 现场 | 语义 |
|---|---|---|
| `tgkill(1000, 4, 64)` | `0x2270f8` 先 `sigaction(64)`，再调 `0x2a0440`：`getpid`/`gettid`/`tgkill` | 自测 SIGRTMAX 往返，探测信号是否可达 |
| `nanosleep({0, 5 ms}, 0)` | `0x1fba10` 的 `usleep(5000)`（`0x29f718` 把 usec 转 timespec） | 初始化节拍 |
| `ioctl(3, TCGETS)` | libc `isatty()` → `tcgetattr()` → `__ioctl` | 判断 fd 3 是否终端 |

`MS.a()V` 保持不变：APK 里确实没有这个方法，真机同样抛
`NoSuchMethodError` 后继续，gate 已把它固定为唯一允许的事件。

## 3. 参照 DuckDroid

- `nanosleep` / `clock_nanosleep`：读 timespec、校验、清 rem，然后
  `AdvanceSleep(ns)`。**不真实睡眠**：注入模式把时长加到注入时钟上；宿主
  模式记一个 sleep offset，之后的时间读数整体前移。
- `kill` / `tkill` / `tgkill`：直接返回 0。运行时没有信号投递模型
  （`sigaction` / `sigprocmask` 本来也是接受后忘记），返回 `ENOSYS` 只会让
  目标走错误的回退分支。
- `ioctl`：VFS 层处理，未知 fd 返回 `EBADF`，已知 fd 返回 `ENOTTY`；不按
  request 解析。对普通文件/管道这正是内核对 `TCGETS` 的答案。

## 4. 改法

1. `RuntimeClock::advanceSleep(ns)`：注入模式加到存储值，宿主模式加 sleep
   offset；`nextRealtimeNs` / `nextMonotonicNs` 在宿主模式把 offset 加回去。
2. `misc_handlers`：新增 `nanosleep(101)`、`clock_nanosleep(115)`
   （与 DuckDroid 一致，忽略 clockid/flags，按相对时长处理）、
   `kill/tkill/tgkill(129/130/131)` 返回 0。
3. `fs_handlers`：新增 `ioctl(29)`，`fd` 未打开 → `EBADF`，否则 `ENOTTY`。
4. gate：`04c_syscalls` 覆盖时钟推进/rem 清零/EINVAL/EFAULT、`isatty`、
   `ioctl` 的 `ENOTTY`/`EBADF`、`kill` 与 `raise`；`runtime_clock_test`
   覆盖 `advanceSleep` 的注入/宿主两条路径；`07g_dy7_plugin` 增加
   `SvcListener` 断言，要求 metasec 的初始化与签名不产生任何
   `unsupported` syscall/host stub。
5. 日志级别：`common/log` 的默认值与 `system`/`worker` 的显式设置都改为
   `Error`，WARN 不再进 stderr。dy7 runner 里直接 `fprintf` 的严格 Java
   事件也改为默认关闭，需要时设 `DY_JNI_EVENTS=1`。

`MS.a()V` 的 JNI 警告保留。

## 5. 验证

- 全量 `ctest --test-dir build`：**49/49**；`07g_dy7_plugin` 通过，
  稳定头仍为 `X-Argus: gEbdag==` / `X-Khronos: 1792886400`。
- `04c_syscalls` 新增：nanosleep/clock_nanosleep 推进注入时钟、rem 清零、
  `EINVAL`/`EFAULT`；`isatty(0)` 与 `/dev/null` fd 的 `ENOTTY`、未知 fd 的
  `EBADF`；`kill`/`raise(SIGRTMAX)` 返回 0。`runtime_clock_test` 新增
  `advanceSleep` 的注入/宿主两条路径。
- `build` / `build-werror` 全绿；`build-asan`（ASan+UBSan）下新增的
  `04c_syscalls` 与 `runtime_clock_test` 通过。`07g_dy7_plugin` 在
  ASan+UBSan 组合里仍停在 Unicorn softfloat 的
  `left shift of 1 by 31 places`（第三方、已知，见 M8/抖音接入 devlog），
  失败前已跑完签名且未报任何 `unsupported`。
- 单次签名 stderr 从 4 条 WARN 降到 **0 字节**（`Error` 级别；`MS.a()V`
  仍由运行时记录，只是不显示）。`DY_JNI_EVENTS=1` 可按需打印该事件：

```text
X-Argus: gEbdag==
X-Khronos: 1792886400
stderr: (empty)
# DY_JNI_EVENTS=1
jni missing-method class=.../MS name=a sig=()V slot=113 tid=4
```

## 6. JNI 面审计

用临时打点（跑完已撤）统计一次签名的 JNIEnv 槽位与方法查找：

| 面 | 结果 |
|---|---|
| 槽位 | 18 种：`ExceptionCheck`、`DeleteLocalRef`、`CallStaticObjectMethodV`、`NewStringUTF`、`GetObjectRefType`、`EnsureLocalCapacity`、`GetObjectClass`、`GetMethodID`、`CallObjectMethodV`、`GetArrayLength`、`GetStaticMethodID`、`GetByteArrayRegion`、`FindClass`、`NewGlobalRef`、`GetSuperclass`、`ReleaseStringUTFChars`、`RegisterNatives`、`GetStringUTFChars`；**没有一条 `UnsupportedFunction`** |
| 成功查找 | `String.getBytes`、`Context.getPackageName`、`MS.b(longSig)`、`MS.a(longSig)`、`Thread.currentThread`、`Thread.getStackTrace`、`System.getProperty`、`Long.valueOf`、`Boolean.valueOf` |
| 唯一失败 | `MS.a()V` |
| 属性 | 只查了 `java.vm.version`，平台包返回 `2.1.0`（与参考 runner 一致） |

`MS.a()V` 确实不是本次漏补：`dexdump classes21.dex` 显示
`com/bytedance/mobsec/metasec/ml/MS` 只有 `<init>()V`；父类 `MS0` 只有
`Bill/Louis/Zeoy/Francies`；`ms/bd/c/k3` 只有 `a`/`c`（native）与 `b`
（Java）。整条继承链都没有 `()V` 的 `a`，真机同样得到
`NoSuchMethodError`。补一个假方法会让 Java 世界偏离设备，gate 也把这条
事件固定为“唯一允许”，因此保留。

顺带确认：本包把 `k3.b` 声明在 `k3` 上（与 APK 的 `k3` 完全一致），native
从 `MS` 查找时经 `findMethod` 的父类遍历命中，行为与真机一致；参考 runner
把 `b` 挂在 `MS` 上是另一种等价写法。
